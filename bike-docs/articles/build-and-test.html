Build & Test Reference

Prerequisites

  • .NET 8 SDK (or newer)
  • Unity Hub with Unity 2022.3.50f1 (legacy unity/) or Unity 6000.0.40f1 LTS (unity-v2)
  • DocFX for building this documentation site
# Install DocFX globally
dotnet tool install -g docfx

Build everything

dotnet build Bike.sln

Expected output: Build succeeded. 0 Warning(s). 0 Error(s).

The solution includes:

  • Bicycle.Physics (netstandard2.1)
  • Bicycle.Physics.Tests (net8.0)
  • Bicycle.Physics.Benchmarks (net8.0)
  • Bicycle.Physics.PlaybackHarness (net8.0)
  • Bicycle.World (netstandard2.1)
  • Bicycle.World.Tests (net8.0)

Run the test suite

# Physics library tests (expect 67/67)
dotnet test src/Bicycle.Physics.Tests

# World library tests (expect 5/5)
dotnet test src/Bicycle.World.Tests

# All tests
dotnet test Bike.sln

The test suite includes:

  • Eigenvalue benchmark — numerical linearization + MathNet EVD vs. Meijaard 2007 Table 2 at multiple speeds. Gate: <1% relative error (we achieve ~1e-6).
  • Allocation-free gate — 100,000 Step() calls with GC.GetAllocatedBytesForCurrentThread() assertion. Fails if any new managed heap allocation is introduced.
  • Determinism gate — two simulators from same initial state produce bit-identical output after N steps.
  • Behavioral scenarios — coast-stable, steer-left-turns-left, drive-accelerates, brake-decelerates, etc.
  • PhysicsBridge round-trip — tests that ToUnity and FromUnity are inverses for all cardinal axes.

Performance baseline

dotnet run -c Release --project src/Bicycle.Physics.Benchmarks

Expected: ~3 µs per Step() on a modern CPU. Takes ~1 minute to run (BenchmarkDotNet warmup + sampling).

Replay a recorded input trace

dotnet run --project src/Bicycle.Physics.PlaybackHarness -- inputs.json out.csv

The playback harness replays a JSON input trace and emits a CSV of all state/snapshot values. Used for headless regression testing of feel-tuning changes.

Codegen pipeline

Only needed when changing the physical model (not during game iteration).

python -m venv tools/eom-codegen/.venv
tools/eom-codegen/.venv/Scripts/Activate.ps1
pip install -r tools/eom-codegen/requirements.txt
python tools/eom-codegen/derive.py
python tools/eom-codegen/emit_csharp.py
git diff src/Bicycle.Physics/Runtime/Generated/   # review changes before committing

This regenerates:

  • src/Bicycle.Physics/Runtime/Generated/WhippleEOM.cs (~1100 lines of straight-line FLOPs)
  • src/Bicycle.Physics/Runtime/Generated/WhippleKinematics.cs

The generated files are committed to git. The .NET build does not invoke Python at runtime.

Unity batchmode tests (unity-v2)

& "C:\Program Files\Unity\Hub\Editor\6000.3.15f1\Editor\Unity.exe" `
    -batchmode -nographics `
    -projectPath unity-v2 `
    -runTests -testPlatform EditMode `
    -testResults out.xml `
    -logFile -

IMPORTANT: Do NOT pass -quit with -runTests. Unity Test Framework manages its own exit lifecycle. See Gotcha 16.

Documentation site

# Build the static site (output at docs/docfx/_site/)
docfx docs/docfx/docfx.json

# Build and serve locally (opens at http://localhost:8080)
docfx docs/docfx/docfx.json --serve

The _site/ directory is gitignored — it is build output, not source. All source is under docs/docfx/ and is committed.

Branch workflow

  • Feature work lives in feat/<name> branches.
  • PRs are opened against main.
  • Each PR requires: dotnet build clean, all xUnit tests green, Unity EditMode/PlayMode tests green (where applicable).
  • The eigenvalue gate and allocation-free gate are non-negotiable — they run on every PR.
